# 스트리머 규칙과 웹 콘솔 관리

작성: 2026-09-21. 요구사항과 저장 계약을 정의하고 초기 코어에 반영했다.
**관리 화면·DB 저장·게임 효과 실행은 아직 구현 전**이다.

전체 구현 기준은 [최종 설계 v1](final-design.md)이다. 여기서는 규칙 입력과 저장 계약을 자세히 다룬다.
후원 내역과 방송 중 수동 조작의 화면·API·충돌 처리는 [스트리머 운영 콘솔](operator-console.md)을 따른다.
전달 이미지 기준 26칸 판, 크기·배치·내용·동작 타입은 [보드 설계](board-design.md)를 따른다.

## 1. 데이터로 관리해야 하는 것

각 채널의 후원 규칙은 `개수 → 동작`을 DB에 저장한다. 배포 코드에 33/52/53 등의
분기나 특정 한글 명칭을 넣지 않는다. 코어가 제공하는 범용 실행 종류는 주사위,
미션, 아이템 지급, 목적지 선택이다. 어떤 개수가 어떤 동작을 호출하는지는 데이터다.

웹 관리 콘솔은 스트리머 또는 위임받은 운영자가 다음을 직접 관리할 수 있어야 한다.

| 관리 대상 | 편집 항목 |
| --- | --- |
| 후원 규칙 | 규칙 이름, 정확한 별풍선 개수, 활성/비활성, 동작 종류 |
| 주사위 | 규칙별 횟수, 별도 연차 활성화 |
| 미션 | 화면에 표시할 문구, 실드 허용 여부, 사용할 아이템, 필요한 개수 |
| 아이템 | 이름, 지급 개수, 보유량 표시; 실제 수량 추가/차감/직접 지정, 증감/사용 이력 |
| 목적지 선택 | 운영자/후원자 채팅/둘 다, 채팅 명령어 |
| 보드 | canvas 크기, 외곽 행/열·자유 배치, 칸 추가/삭제·path·문구·모양, 도착/통과 type·매개변수·실드 |
| 중앙 콘텐츠 | 주사위·현재 미션·보상 현황·후원 알림·방향·문구·이미지/Lottie 위젯과 위치/크기 |
| 연출 | Lottie 자산 업로드·검증·미리보기·버전, 동작별 자산 연결·marker·속도·크기·색상·길이 |
| 화면 품질 | 품질 preset, 선택적 3D, 동시 효과 수·연출 생략·OBS 레이아웃 |
| 운영 화면 | 후원 내역/검색/상세, 실제 수동 주사위, 현재 방향·위치·lap, 미션/대기열·세션 제어 |

규칙 신규 추가·수정·삭제는 코드 수정이나 재배포 없이 완료되어야 한다.
관리자가 JSON 파일을 고치는 것만으로 이 요구를 완료했다고 판단하지 않는다.
동작 구현에 임의 코드를 입력하는 방식 대신 검증 가능한 설정 폼을 사용한다.

## 2. 초기 규칙

아래 7개 개수와 명칭은 사용자 제공값으로 확정했다.
첫 설정 가져오기에 사용할 프리셋은 `presets/streamer-initial.json`이다.

| 개수 | 규칙명 | 초기 동작 |
| --- | --- | --- |
| 33 | 주사위 굴리기 | 주사위 요청 1회 |
| 52 | 안주 먹어 | 해당 문구의 미션 |
| 53 | 안주 안돼 | 해당 문구의 미션 |
| 100 | 무조건 한잔해 | 해당 문구의 미션; 실드 허용 여부 편집 |
| 101 | 한잔 실드 | 설정한 실드 아이템 1개 지급 |
| 152 | 같이 한잔 | 해당 문구의 미션; 실드 허용 여부 편집 |
| 486 | 원하는 칸으로 | 운영자와 해당 후원자의 채팅 선택을 모두 허용하는 요청 |

주사위 외 규칙은 별도 주사위를 굴리지 않는다. 66/99를 33의 배수로 계산하지 않고,
200/250도 미등록인 동안 동작하지 않는다. 연차 등록은 별도 설정이다.

52/53의 지속시간이나 해제 규칙은 아직 정해지지 않았다. 최초에는 운영자가 확인하는
미션으로 표현하며 무기한 안주 허용/금지 상태라고 단정하지 않는다. 지속 효과로
확장할 때에는 기간/해제 조건도 편집 가능한 설정으로 추가한다.

프리셋 적용은 채널 생성/명시적 가져오기 때의 작업이다. 시스템이 시작할 때마다
upsert하여 스트리머가 바꾼 값을 초기값으로 돌려놓지 않는다. 가져오기 화면은 기존
설정과의 충돌/변경을 미리 보여주며, 기존 설정이 있으면 자동 덮어쓰지 않는다.

## 3. 한잔 실드

사용자 확인: 한잔 미션을 막는 아이템이며, '무조건 한잔해'를 막을 수 있는지는
운영자가 선택할 수 있어야 한다. 따라서 표시 이름이나 100이라는 개수에 예외를
하드코딩하지 않고 모든 미션에 동일한 정책을 적용한다.

- `shield: null`: 실드 사용 불가.
- `shield: { itemId, quantity }`: 지정한 아이템을 해당 개수만큼 사용하면 미션 방어 가능.
- 후원으로 나온 미션과 보드에서 나온 미션은 같은 정책을 사용한다.
- 아이템 정의/지급량/미션별 비용은 설정값이다. '한잔 실드'는 초기 아이템 이름일 뿐이다.

초기 프리셋의 **제안값**은 '무조건 한잔해' 실드 불허, '같이 한잔' 실드 1개로
방어 가능, 101개 후원 시 실드 1개 지급이다. 실제 방송 룰은 관리 화면에서 바꿀 수 있다.
실드 보유 주체는 공유 말에 연결된 세션 인벤토리로 시작하는 안을 제안한다.

게임 실행 시에는 미완료 미션 선택 → 실드 사용 요청 → 정책/잔량 검증 → 미션 상태와
재고를 함께 확정한다. 운영자 확인 방식으로 시작하는 안이며 자동 소비를 몰래 추가하지 않는다.
같은 요청 재전송, 완료 버튼과 실드 버튼 동시 클릭에서 재고가 두 번 차감되지 않도록
트랜잭션·유일 명령 키·미션 상태 전이를 적용한다. 과거 미션의 정책은 발생 당시 값을 보관한다.

## 4. 원하는 칸으로

사용자 확인: 운영자 선택과 후원자 채팅 선택을 **모두 지원**한다.
설정에는 `operator`, `donor_chat`, `both`가 있으며 초기 프리셋은 `both`다.
채팅 명령어 초기안은 `!이동`으로 두되 편집할 수 있다.

후원이 들어오면 즉시 임의의 칸을 고르는 대신 고유한 이동 요청을 생성한다.

1. 운영자는 웹 콘솔의 대기 요청에서 칸을 선택·확정한다.
2. 해당 후원자는 같은 방송 채팅에서 `!이동 <요청번호> <칸번호>`로 선택할 수 있다.
   본인에게 대기 요청이 하나뿐이면 요청번호 생략을 지원하는 안을 제안한다.
3. 수집기가 준 안정적인 플랫폼 userId로 요청 소유자를 확인한다. 닉네임만 비교하거나
   사용자가 입력한 임의 userId를 신뢰하지 않는다.
4. 요청이 만들어진 보드/세션에서 유효한 칸인지 확인하고 서버가 이동을 확정한다.
5. 웹과 채팅이 경합하면 같은 요청의 `pending → resolved`를 먼저 커밋한 한 건만 성공한다.
   이후 입력은 이미 처리됨으로 응답하며 말이 다시 움직이지 않는다.

보드 변경, 요청 취소·만료, 세션 종료 뒤 입력은 거부한다. 잘못된 채팅은 요청을
소비하지 않으며 운영자 화면으로 수동 처리할 수 있다. 만료 시간과 이동 후 도착 칸의
미션 실행 여부, 지나간 칸/출발점 처리 방식은 효과 구현 시 편집 가능한 옵션으로 정한다.
대기 중 다른 이동과의 순서는 세션 명령 큐에서 보장한다.

## 5. 저장과 변경 적용

DB에는 채널별 설정 aggregate와 단조 `revision`을 저장하고, 내부 config의
`schemaVersion`과 별개로 관리한다. 코어가 받는 config에는 revision/권한 메타데이터를
섞지 않고 API envelope에 둔다.

제안 API:

```text
GET  /v1/channels/:channelId/game-config
PUT  /v1/channels/:channelId/game-config     { expectedRevision, config }
POST /v1/channels/:channelId/game-config/preview
POST /v1/channels/:channelId/move-requests/:requestId/resolve
POST /v1/channels/:channelId/missions/:missionId/use-shield
```

위 경로는 설계이며 현재 구현된 endpoint가 아니다. 규칙 수가 적은 초기에는 전체 설정을
한 트랜잭션으로 검증·저장한다. 행 추가/삭제는 UI에서 하고 저장 시 새 revision을 만든다.
중복 개수/ID, 잘못된 정수·동작, 사라진 아이템 참조를 거부한다. 다른 관리자가 먼저
저장한 경우 revision 충돌을 반환하고 변경 내용을 덮어쓰지 않는다.

채널 권한, 수정자·시각·이전/새 revision을 기록한다. 설정 저장과 변경 알림 outbox를
같은 트랜잭션으로 남긴다. 저장 이후 새로 수락하는 후원에는 새 규칙을 사용하고,
이미 수락한 미션/연차/이동 요청에는 당시 이름·동작·실드 정책 snapshot을 유지한다.
보드 구조는 세션 시작 시 고정하고 편집한 구조는 다음 세션부터 적용한다.
연출 설정은 별도 버전으로 게시하며 이미 재생 중인 cue의 자산을 교체하지 않는다.

## 6. 설정 편집과 방송 중 운영의 구분

채널 설정은 다음 요청이나 새 세션의 기본 규칙이고, 운영 명령은 현재 세션의 상태를 바꾸는 작업이다.
`아이템 지급 기본값 1→2`와 `현재 실드 수량 1→2`, `새 세션 기본 방향`과 `현재 방향`을 같은 저장 버튼으로
혼합하지 않는다. 실제 재고·위치·방향을 GameConfig JSON에 직접 덮어쓰지 않는다.

스트리머는 운영 페이지에서 실시간 후원과 무동작 사유를 확인하고, 보상 수량 증감/지정·수동 주사위·
정/역방향·칸 위치/거리 보정·미션 처리·대기열 보류/취소를 직접 수행한다.
술 적립/정산, 이동 배수/횟수, 무인도 제한, 세계여행 예약도 조회·조정·해제/취소할 수 있어야 한다.
초기 술 적립은 +1잔, 청산은 전량 단일 미션, 두 배는 다음 주사위 이동 1회의 거리 ×2다.
설정의 적립 단위/기본 지급량과 현재 잔 수를 구분하고 예약된 청산량보다 낮은 총량 보정을 거부한다.
수량 조정에는 재고 원장과 revision을, 수동 이동/방향 변경에는 결과와 대상 revision을 기록한다.
모든 조작은 서버에 영속 수락되고 다른 콘솔과 OBS에 반영되며 브라우저에서만 상태를 바꾸지 않는다.

수동 주사위는 실제 게임에 적용되고 운영자 출처로 기록한다. 테스트용 규칙 미리보기는 별도 세션이다.
방향은 다음 미확정 이동부터 적용하고, 직접 위치 보정은 기본적으로 자동 이동 일시정지와 함께 수행한다.
위치 보정은 이전 연출을 무효화하지만 완료된 후원 결과나 대기 중인 486을 삭제하지 않는다.
일시정지 중 받은 목적지 선택도 실제 이동은 대기한다. 상세 정책과 첫 출시 인수 기준은 운영 콘솔 문서에 있다.

## 7. 완료 기준

- 관리 화면에서 7개 초기 규칙을 가져오고 저장한 뒤 재시작해도 그대로 유지된다.
- 33→34 변경 후 33은 미동작, 34는 설정한 주사위 동작으로 실행된다.
- 규칙을 추가·삭제하거나 문구/종류/활성 여부를 바꿀 수 있다. 코드 배포는 필요 없다.
- '무조건 한잔해'의 실드 허용/불허를 저장해 실제 미션 처리가 달라진다.
- 보유량 부족이나 중복 사용으로 실드 재고가 음수가 되지 않는다.
- 운영자와 후원자 채팅 모두 같은 이동 요청을 확정할 수 있고, 경합해도 한 번만 이동한다.
- 타인의 채팅, 같은 닉네임, 만료·중복 요청, 잘못된 칸 번호는 말 위치를 바꾸지 않는다.
- 설정 미리보기는 실제 세션 상태나 인벤토리를 바꾸지 않는다.
- 후원 내역에서 실행·무동작·실패와 운영 보정 이력을 확인하고 검색/필터할 수 있다.
- 보상 증감/최종 수량 지정·수동 주사위·방향/위치 변경이 실제 DB와 OBS에 반영된다.
- 동시 운영·재전송·연출 재생 중 보정에도 중복 지급/이동이나 낡은 상태 덮어쓰기가 없다.

현재 완료한 것은 후원/26칸 보드 프리셋, 설정 검증, 정확 개수 매칭, 보드 좌표/경로 미리보기와 회귀 테스트다.
DB/API/웹 콘솔, 실드 재고·미션 실행, 채팅 파싱·이동 요청 확정과 위 운영 기능은 다음 구현 범위다.
